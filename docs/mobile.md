# Мобильные уведомления UnderCtrl

После сканирования QR-кода устройство получает новые критические инциденты той же панели, что и координатор. Один аккаунт может подключить несколько устройств.

**Адрес API после выкладки** — `https://cybergarden.sosmooth.ru/api/v1`. Для тестового стенда замените домен. В QR зашита только строка `code`. Адрес сервера задаёт конфигурация приложения. На одном стенде Android-клиент и сервер должны использовать один Firebase-проект. Для этой установки это [underctrl-d087a](https://console.firebase.google.com/project/underctrl-d087a/overview).

## Подключение Android

1. Зарегистрируйте Android-приложение с его package name в Firebase-проекте и подключите клиентский `google-services.json`. Создайте канал «Критические сбои». На Android 13+ запросите разрешение `POST_NOTIFICATIONS` при включении уведомлений. [Настройка Firebase для Android](https://firebase.google.com/docs/cloud-messaging/android/get-started)
2. Получите идентификатор установки, зарегистрированной в **FCM**. Для SDK с регистрацией по FID используйте значение `onRegistered(installationId)` и передавайте `fcmTargetType: "fid"`. SDK с registration token передаёт результат `getToken()` с типом `"token"`. Firebase ID token авторизации сюда не подходит. [Регистрация установки](https://firebase.google.com/docs/cloud-messaging/android/get-started)
3. Координатор входит в личный кабинет и нажимает **«Подключить телефон»** над профилем. Панель выдаёт одноразовый QR на пять минут. Каждый новый QR заменяет предыдущий код аккаунта.
4. Отсканируйте QR в приложении и вызовите `POST /mobile/devices`. Передавайте исходный текст QR без преобразований. В примерах ниже угловые скобки обозначают значения для подстановки.

```http
POST /api/v1/mobile/devices
Content-Type: application/json

{"code":"<текст QR>","platform":"android","fcmTargetType":"fid","fcmToken":"<зарегистрированный FID>"}
```

Ответ `201 Created`

```json
{"deviceId":"4bafb868-8e44-4458-ac61-7b35ca4ef101","deviceToken":"<секрет этой установки>"}
```

5. Сохраните `deviceToken` в защищённом хранилище приложения. Сервер выдаёт его один раз. Этот ключ разрешает обновить адрес доставки или отключить собственное устройство. Логин, пароль и cookie координатора телефону не нужны.
6. При смене регистрации передавайте новый FID из `onRegistered` либо registration token из `onNewToken`. Если колбэк пришёл до сканирования, используйте последнее значение при регистрации. При временной потере сети повторите обновление.

```http
PUT /api/v1/mobile/devices/current/token
Authorization: Bearer <deviceToken>
Content-Type: application/json

{"fcmTargetType":"fid","fcmToken":"<текущий FID>"}
```

Успешный ответ — `204 No Content`. Чтобы отключить телефон, отправьте `DELETE /api/v1/mobile/devices/current` с тем же заголовком. После `204` удалите локальный ключ. Если ключ утрачен или ответ регистрации потерялся, отключите прежнюю привязку в кабинете и отсканируйте новый QR.

## Маршруты

Все пути в таблице начинаются с `/api/v1`. Для запросов с JSON укажите `Content-Type: application/json`. Не записывайте в логи код, Bearer или адрес регистрации Firebase.

| Кто вызывает | Метод и путь | Успешный результат |
|---|---|---|
| Кабинет с личной cookie-сессией | `POST /mobile/pairings` | `201 {code, expiresAt}`. Время в UTC. Тело запроса пустое. |
| Устройство с кодом из QR | `POST /mobile/devices` | `201 {deviceId, deviceToken}`. Параметры — `code`, `platform`, `fcmToken`, необязательный `fcmTargetType`. |
| Устройство с Bearer | `PUT /mobile/devices/current/token` | `204`. Заменяет регистрацию Firebase, в том числе после ответа FCM `UNREGISTERED`. |
| Устройство с Bearer | `DELETE /mobile/devices/current` | `204`. Отзывает эту привязку. |
| Кабинет с личной cookie-сессией | `GET /mobile/devices` | `200 {items:[{deviceId,platform,createdAt,pushEnabled}]}`. Показывает устройства текущего аккаунта. |
| Кабинет с личной cookie-сессией | `DELETE /mobile/devices/{deviceId}` | `204`. Можно отключить и потерянный телефон. |

Значения `platform` — `android` и `web`. `fcmToken` — непрозрачная строка, 1–2048 печатных ASCII-символов без пробелов. Поле `fcmTargetType` принимает `fid` или `token`, по умолчанию `token`. Указывайте тип при каждом обновлении. Отключение учётной записи координатора отзывает привязки. Уже принятый Firebase push может дойти до устройства после отзыва.

| Код ответа | Действие клиента |
|---|---|
| `400 VALIDATION_ERROR`, `415 UNSUPPORTED_MEDIA_TYPE` | Проверить JSON, значения полей и заголовок Content-Type. |
| `401 MOBILE_PAIRING_INVALID` | Получить новый QR. Предыдущий мог истечь, использоваться или быть заменён. |
| `401 MOBILE_DEVICE_UNAUTHORIZED` | Удалить утративший силу локальный ключ и предложить повторное подключение. |
| `409 FCM_TOKEN_IN_USE` | Регистрация уже привязана. Для своей установки обновить её с сохранённым Bearer либо отозвать старую привязку. После конфликта QR действует до обычного срока. |
| `404 MOBILE_DEVICE_NOT_FOUND` | Обновить список устройств в кабинете. |
| `503 MOBILE_PUSH_DISABLED` | На этом стенде мобильные уведомления выключены. |

## Что приходит в push

Событие `critical.raised` означает переход в активный P1. В источнике это `priorityId = 4` и состояние `Assigned`, `WorkInProgress` или `Research`. Пуш появится для нового активного P1, повышения до P1 или повторного открытия. Загрузка исходного архива, повтор того же импорта, обычное редактирование P1 и закрытие сами по себе пуша не создают. Новая привязка получает события, возникшие после подключения.

Android получает **data-сообщение высокого приоритета**. В `FirebaseMessagingService.onMessageReceived` сразу покажите системное уведомление с `data.title` и `data.body`. Для `NotificationManager.notify(tag, id, notification)` можно использовать `notificationId` как строковый `tag` и постоянный числовой `id`. Тогда новый инцидент создаст отдельную карточку, а повтор доставки обновит ту же. [Получение сообщений FCM](https://firebase.google.com/docs/cloud-messaging/android/receive)

Пример `RemoteMessage.data`. Все значения — строки.

```json
{
  "type": "critical.raised",
  "notificationId": "42",
  "incidentId": "INC123",
  "sysId": "001",
  "title": "Критический сбой",
  "body": "Инцидент INC123"
}
```

Считайте `notificationId` ключом дедупликации. Если исходный идентификатор превышает 256 байт, соответствующее поле `incidentId` или `sysId` пустое. Бэкенд хранит задания в PostgreSQL и повторяет временно неудачные отправки в пределах часа с момента события. Доставка зависит от Firebase, сети и разрешений устройства.

## Веб-приложение для iPhone

Используйте те же маршруты с `platform: "web"`. Для веб-пушей нужны HTTPS, регистрация в FCM через service worker и публичный VAPID-ключ того же Firebase-проекта. Сервер отправляет заголовок и текст в `webpush.notification`, а также `data`. При автоматическом показе SDK не создавайте вторую карточку в обработчике. На iOS 16.4+ пользователь добавляет веб-приложение на домашний экран и выдаёт разрешение после нажатия кнопки. [Firebase Web](https://firebase.google.com/docs/cloud-messaging/web/get-started) · [WebKit](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/)

## Проверка на устройстве

На тестовом стенде выполните исходный импорт, подключите телефон, сверните приложение и повысьте приоритет одного активного тестового инцидента до 4. Должна появиться одна карточка с номером инцидента. Повторите тот же импорт, затем отключите телефон из кабинета и создайте ещё один активный P1. Новая карточка после отключения появляться не должна.
